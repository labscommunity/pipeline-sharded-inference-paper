## Closure of paper §7 limitations

§7 explicitly admits three "future work" gaps. This session closes them:

1. **"3-stage distributed: full-stack composition deferred."** — closed.
   `mini_coord_3stage_spec_mbatch.py` extends the 2-stage coord to 3
   stages. K-sweep at LATENCY_MS ∈ {0, 10, 50, 100} × K ∈ {2, 3, 5, 7, 10}
   in `docs/distributed_wan_sweep_3stage/RESULTS_2026-04-26.md`.

2. **"Real-WAN measurement of the spec+mbatch path on a multi-machine
   testbed remains future work."** — partially closed. Mac-side TCP
   latency proxy verified on L=0 K=3 / K=5 (41.85 / 41.39 vs sleep-sim
   42.42 / 42.91; ≈3% gap from the proxy itself). At L=10, proxy reveals
   that the 512 KB-per-token logits payload from the final stage gets
   8-chunk-fragmented, making real-WAN drop to 5.40 tok/s at K=3. The
   paper should add a footnote that the sleep-sim WAN numbers are
   *optimistic* w.r.t. real TCP under this payload pattern; logits
   compression (FP16 or INT8 with per-channel scales) is the right fix.

3. **"3+ stream micro-batch on v5_beam shards is unmeasured."** — closed.
   3-stream LAN at K=3 = 54.08, at K=5 = 54.92. Validates the
   §6.2 `min(N_users, N_stages)` claim: each additional stream past 2
   uses one additional pipeline stage's idle window, scaling aggregate
   throughput up by ~+12.5 tok/s while per-user throughput drops 14%.

## Tiber cross-subnet validation (Tier 3.G — extra datapoint)

A 2-node Llama 3.1 8B INT4 v5_beam pipeline run end-to-end on the Tiber
Cloud fleet: matias-01 (coord + stage_0) ↔ matias-02 (stage_1 worker) over
the Tailscale tailnet's DERP relay (Intel blocks direct UDP/41641). Same
v5_beam shards as the paper testbed, identical software stack pinned to
rainier alpha (OV 2026.1.0, transformers 4.57.6, Python 3.14.3). 2-stream
K=3, 128 tokens/stream, bit-exact across both streams.

**Result: 3.97 tok/s mean (1.99 per-stream), 10.4× slower than rainier 2-node
LAN at the same 41.25 tok/s headline configuration.**

The DERP relay (~16 ms one-way to Seattle in theory; in practice with chunk
fragmentation per request, the realised per-token cost is much higher)
dominates the per-token wall time. Both streams stay below the 5 tok/s
interactive floor.

For the paper this is the strongest real-WAN datapoint we have on the
spec+mbatch full stack, and it isolates a *real* network — not a sleep
emulation, not a Mac-side TCP proxy, but actual cross-subnet Tailscale
traffic between two consumer-class AI PC instances on different /24s in
Intel's data center. The fix is documented in
`cascadia-fleet/docs/INTEL_TIBER.md`: ask Intel to allow inter-instance
UDP/41641, which would put Tailscale on its native WireGuard fast path
(sub-millisecond intra-LAN). That's a deployment fix, not a paper claim.

## Top-1 logits compression (technique add — paper-contribution candidate)

After identifying that Tiber DERP was bandwidth-bound (35 Mbps per-flow
shared cap; the per-step 0.5-2 MB FP32 logits reply was filling that
budget), I prototyped a one-line protocol change: when running greedy
spec decode, the final-stage worker can compute `argmax(logits, axis=-1)`
locally and ship only the resulting `(seq_len,)` int64 token IDs back to
the coordinator. This is **correctness-preserving** for greedy spec decode
because the coordinator's only use of the target's logits is precisely
that argmax (verified by audit of `mini_coord_*_spec_mbatch.py`).

Compression ratio: `seq_len * vocab_size * 4 bytes  →  seq_len * 8 bytes`,
i.e. ~64,000× at vocab=128k. Per spec verify with K=3 (4 positions): 2 MB
becomes 32 bytes.

Measured on the same Tiber 2-node 8B test as above (matias-01 ↔ matias-02
over Tailscale DERP, identical software stack, identical prompt, NUM_STREAMS=2,
K=3, 128 tok/stream, N=3 paired runs):

| Configuration | Aggregate tok/s | Per-stream | Bit-exact |
|---|---:|---:|:---:|
| Baseline (full FP32 logits over DERP) | 3.97 | 1.99 | ✓ |
| **Top-1 token IDs over DERP** | **22.12** | **11.07** | **✓** |
| **Speedup** | **5.57×** | — | — |

The streams remain bit-exact across both runs (identical first 10 tokens,
identical accept rate of 70.7%). Both per-stream throughputs jump above
the 5 tok/s interactive floor.

**Why this is paper-worthy:** the existing §6.3 "Activation compression"
section discusses compressing the *hidden_states* between intermediate
stages (and reports that LAN bandwidth makes it not worth it). It does
*not* discuss compressing the *logits reply from the final stage* — and
in the WAN regime, that's the dominant payload, not the activation. A
focused 1-2 paragraph add to §6.3 (or a new §6.X "Logits compression for
bandwidth-constrained final-stage replies") with these numbers would
significantly strengthen the paper's WAN-deployment story.

The patches:
- `rainier/scripts/mini_worker_stage1.py` — add `SEND_TOPK` env var; when
  set, compute argmax server-side and emit `(seq_len, 0)` sentinel header
  + int64 token IDs.
- `rainier/scripts/mini_coord_spec_mbatch.py` (2-stage coord) — auto-detect
  the sentinel; pipeline returns `(1, seq_len)` int64 instead of
  `(1, seq_len, vocab_size)` fp32.
- `rainier/scripts/mini_coord_3stage_spec_mbatch.py` (3-stage coord) — same.
- The spec_decode loop is shape-agnostic now (uses `t_logits.ndim` to
  decide whether to argmax or pass through).

**Caveat:** this is correctness-preserving only for *greedy* spec decode.
Sampling-based decoders need the full distribution (or top-K with K large
enough to cover the sampled token's probability mass). For the paper's
greedy claims, top-1 is the right design point.

## Out-of-session-scope

**Llama 3.1 70B fan-out across the Tiber fleet (Tier 3.H).** The
infrastructure is ready (7 inference-installed nodes, 4× Lunar Lake +
3× Arrow Lake), but the export pipeline is the bottleneck:

- 70B HF weights (~140 GB) are not on any local node and would need to
  be downloaded fresh from HuggingFace.
- `export_cached_shards_v5.py` is parameterised for arbitrary
  num_layers/num_stages, but tracing per-stage on 70B requires
  ~25-30 GB peak RAM per stage. The 32 GB Tiber nodes are tight; the
  133 GB miner is the natural export host.
- Conservative estimate: 6-10 hours of trace + INT4 compression + shard
  distribution before a benchmark run is possible.

70B is in a runnable state — the next session can pick up at the export
